# Grodd integration spike: how this connects to Gro's real systems

Status: research and stubs only. **Nothing in `server.js` or `lib/` requires this folder, and no real API call has been made.**
Researched 2026-10-21 from the vendors' own docs (URLs below). Anything marked **verify** was unclear, contradictory, or not read, and must be confirmed with one test call before it is promised to anyone.

## Headline findings (read this first)

1. **Circle (Admin API v2, Headless Member API, Workflows, MCP) needs the Business plan ($199/mo, annual) or higher.** The Professional plan ($89) has none of them. Business includes only **5,000 Admin API requests per month** (extra: $0.005 each); Scale ($419) includes 30,000. Circle MCP calls count toward the same quota. Hard limit: 2,000 requests per 5 minutes per IP. Budget math matters: refreshing a 500-member list (5 pages of 100) hourly is 3,600 calls per month, 72% of Business.
2. **Luma's API and webhooks need Luma Plus ($59/mo, annual).** Gro is on the Free plan, so the REST API is not available to Gro today. Free-plan routes: **Luma's MCP server** (`https://mcp.luma.com`, OAuth as the signed-in user, explicitly "you don't need Luma Plus") and **CSV export of guests** (included in Free; same shape as `data/luma_guests.csv`).
3. **Brevo works on every plan including Free** (API access, `api-key` header, `POST https://api.brevo.com/v3/smtp/email`). Keys have no documented scopes, so least privilege is enforced by our own code, not by the key.
4. **Google Calendar free/busy is a first-class call** (`POST https://www.googleapis.com/calendar/v3/freeBusy`) with a genuine least-privilege scope (`calendar.freebusy`). This is the one integration where the vendor enforces read-only for us.
5. **Circle has no webhook-management endpoint in Admin API v2.** Outbound webhooks are a "Send to webhook" action inside an automation Workflow, configured in the admin UI. Which plan unlocks that action is unclear (**verify**: the pricing page lists "Webhooks" under Scale, not Business).
6. **Circle's own docs contradict each other on the auth header:** Quick start says `Authorization: Bearer <token>`, the OpenAPI spec says `Authorization: Token <token>`. The stub defaults to Bearer and switches with `CIRCLE_AUTH_SCHEME=Token`. **Verify** with one read call.
7. **Luma has no documented draft state for events.** `luma.createEventDraft` approximates one with `visibility: "private"` plus `registration_open: false`. **Verify** on a test calendar.
8. **Terms of service:** use only the official API or MCP, never scrape or script the Circle web UI. Circle's platform terms (`https://circle.so/terms`, conduct section) bar third-party apps that interact with the service without consent, "including any scripts designed to scrape or extract data". I could not find a section 8.4 in Circle's own terms; a clause that matches the "no spiders, robots, crawlers" wording sits in a community-owner terms page that names CircleCo as a beneficiary (`https://mikerhodes.circle.so/terms`), so §8.4 is probably Gro's own community terms (**verify** at Gro's own `/terms`). Either way the official API and MCP are the sanctioned route.

## Least-privilege scopes per Grodd skill

Reality check: **Circle, Luma and Brevo credentials have no documented per-endpoint scopes** (Circle: one Admin V2 token; Luma: one key per calendar; Brevo: one all-access key). Only Google has real scopes. So the controls are: (1) a dedicated credential per system just for Grodd, stored outside the repo, (2) `GRODD_INTEGRATIONS_WRITE` off by default, (3) drafts only, with a human approving in the Grodd queue, (4) Circle MCP "Read only" mode as an option where only reads are needed.

## Six-step rollout

1. **Decide and prepare (no code in production).** Confirm Gro's Circle plan is Business or higher (Developers tab shows the quota). Decide the Luma path: upgrade to Plus ($59/mo), or use Luma MCP / CSV on Free. Authenticate the Brevo sending domain against Gro's Google Workspace domain (DKIM and DMARC records). Create one dedicated token per system, held in a secret manager. Confirm the ToS reading above and the GDPR basis for Pulse (opt-in, DPA with each processor).
2. **Read-only shadow mode.** Turn on `listMembers`, `findMemberByEmail`, `listEvents`, `listAllGuests`, Google `freeBusy` behind a flag. Grodd answers from live data but writes nothing. Compare against `data/members.csv` and `data/luma_guests.csv` for parity. Cache with a TTL sized to the Circle quota (members at 6 h or longer, or refresh from webhooks later). Success check: member-check output matches a manual check on one real event.
3. **Draft-write in staging.** Set `GRODD_INTEGRATIONS_WRITE=1` only on staging against throwaway spaces and calendars. Create Circle post and event drafts, a private Luma event, a Brevo campaign draft. Each Grodd queue item links to the draft in the native UI; a human publishes or sends there. Settle every **verify** item in the table with real test calls and update this file. Store the returned object ids locally so a retry cannot create a duplicate (no idempotency key is documented: **verify**).
4. **Approved publish (optional, per action).** Only after step 3 is clean: a human click in the Grodd queue triggers the publish step (Circle `PUT /events/{id}` with status published, Luma `events/update`, Brevo campaign send, Google `events.insert` with a room). One approval authorises one action; keep a global kill switch.
5. **Webhooks instead of polling.** Luma `guest.registered`, `guest.updated`, `guest.refunded` to a Grodd endpoint: verify the signature with `luma.verifyWebhookSignature`, answer 2xx within 5 seconds, dedupe on `Webhook-Id`. Circle: a Workflow with a "Send to webhook" action (plan and signing **verify**); since signing is undocumented, treat the payload as a hint and re-fetch the object with the Admin API before acting. Webhooks cut API usage sharply, which is the explicit advice in Circle's best-practices page (https://api.circle.so/apis/admin-api/usage-and-limits/best-practices).
6. **Harden and operate.** Honour 429 with `Retry-After` (Luma also sends `X-RateLimit-*`); log every outbound call (method, path, status, never headers or bodies with personal data); alert at 80% of the monthly Circle quota; rotate tokens each quarter; per-skill allowlists as in the table above; written runbook for revoking each token; decide whether to move to Circle MCP or Luma MCP as the transport so Gro keeps the vendor-managed OAuth and read-only modes.

1. Circle auth header: Bearer (Quick start) vs Token (OpenAPI).
2. Which member the Circle token acts as, and whether it can be restricted (no scopes documented).
3. Circle "Send to webhook": plan (Business vs Scale), payload shape, signing.
4. Circle post body field (`internal_custom_html` vs `tiptap_body`); event `body` format; `space_id` duplication on event create; `/community_members/search` response on a miss; `member_tag_ids` encoding.
5. Circle Headless Member API: full endpoint list not read.
6. Circle ToS §8.4: could not locate in Circle's own terms; check Gro's own community terms.
7. Luma: no draft state (private plus registration closed is our workaround); `/v1/webhooks/list` is in the docs index but the changelog says v1 webhook endpoints are now undocumented.
8. Luma webhook HMAC key derivation (raw string vs base64) and timestamp unit.
9. Brevo campaign call: `api-key` only, or also the OAuth Bearer header the page lists; free-plan daily cap; campaign rate limit (inferred 100 req/hour).
10. Google: server-side auth (service account with domain-wide delegation was only seen as a requirement for attendees), room resource calendar IDs, and booking a room via attendee.
11. Swish: no mention in Luma API docs; Luma's pricing page lists regional payment methods without naming Swish.
